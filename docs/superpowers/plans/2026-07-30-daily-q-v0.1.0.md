# DailyQ v0.1.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build DailyQ v0.1.0 — daily login-streak rewards, a small server-wide daily-task set, and a claim mailbox — the first slice of the xpfarm questing system.

**Architecture:** A thin `DailyQPlugin` wires focused services over a SQLite store. Pure domain logic (day boundary, streak rules, date-seeded task rotation, reward model) is isolated from the Bukkit runtime so it is fully unit-tested; listeners, commands, and UI are thin adapters over those services. Bedrock uses Cumulus forms behind a Floodgate availability guard; Java uses a chest GUI; both degrade to the Java path when Floodgate is absent.

**Tech Stack:** Java 25, Paper API 26.1.2 build 74, SQLite (`org.xerial:sqlite-jdbc`, runtime via `plugin.yml` `libraries:`), Floodgate API + Cumulus (`provided`, reflection-free but guarded), JUnit 5.

## Global Constraints

Every task's requirements implicitly include this section. Copy it verbatim into every subagent dispatch.

- **Java 25**, compiled against **Paper `26.1.2` build 74** (`paper-api:26.1.2.build.74-stable`, `provided`).
- **`api-version: '26.1'`** in `plugin.yml` — already set; do not change.
- **Maven group `org.xpfarm`**, artifactId `daily-q`, version `0.1.0`. Java package `org.xpfarm.dailyq`.
- **AGPL-3.0-or-later license header** on every new `.java` file (copy the header block already in `DailyQPlugin.java`).
- **Ownership is `carmelosantana`.** Never introduce `herobrinesystems` anywhere.
- **Geyser/Floodgate/ViaVersion safety:** No Java-only chat-input prompts on a path a Bedrock player can reach — use Cumulus forms on Bedrock, chest GUI on Java. Any class importing `org.geysermc.*` is constructed ONLY behind a runtime `Bukkit.getPluginManager().isPluginEnabled("floodgate")` + bridge-availability guard; every Bedrock resolution falls back to the Java path when Floodgate is absent. Resolve player identity through Floodgate (linked vs. unlinked) rather than assuming the online UUID. Do not assume the client's exact protocol version (ViaVersion may be bridging).
- **External services:** NONE in v0.1. Do not add any outbound HTTP/Ollama/Umami calls.
- **Command dispatch-safety (Pizza contract):** every player command is no-argument-runnable, resolves the sender as the acting player, opens a UI, and behaves identically whether typed or dispatched by another plugin with `run-as: player`. Permission checks are enforced at execution, not just registration.
- **Reward model:** concrete item rewards only in v0.1. Design the `Reward` type so a future `TokenReward` slots in without reshaping callers, but do NOT build a token currency or shop now.
- **Tasks are server-wide and date-seeded:** every online player gets the identical daily set for a given server-day. No per-player rotation state.
- **Tests with the code, not after.** Every task that separates logic from the runtime ships its unit tests in the same commit. Follow TDD: failing test first.
- **Persistence is SQLite**, mirroring Farmers Market: `sqlite-jdbc` `provided` + declared in `plugin.yml` `libraries:`, never shaded, `org.sqlite.*` never relocated. All DB work off the main thread via an executor; results returned as `CompletableFuture`.

### Settled facts — do not re-derive, do not "improve"

- Reward delivery is a **claim mailbox**. Nothing is auto-dropped into inventory. Partial claims leave the remainder pending when inventory is full.
- Streak calendar loops every **28 days**; milestone spikes at days **7, 14, 28** (config-driven).
- **Streak rules:** with `forgiveness-misses: 1` — 0 missed days between logins → streak +1; missed days ≤ `forgiveness-misses` → streak **held** (not reset) and a one-time make-up becomes available; missed days > `forgiveness-misses` → streak **steps down by 1, floored at 1** (never 0).
- Daily set = exactly `tasks.per-day` (default 3): one `easy`, one `medium`, one `stretch`, selected deterministically from the pool by the server-day seed.
- **Completion bonus** (all daily tasks done) is granted to the mailbox and is worth more than the sum of the per-task rewards.
- Fired framework events: `DailyTaskCompletedEvent`, `DailyStreakClaimedEvent` (Bukkit events, main thread). No listener ships in v0.1 — they are seams.

## Task 2: Server-day boundary (`DayClock`)

**Files:** Create `time/DayClock.java`; Test `time/DayClockTest.java`.

**Interfaces:**
- Produces: `final class DayClock { DayClock(int resetHour, ZoneId zone, Clock clock); long today(); static long dayFor(Instant instant, int resetHour, ZoneId zone); }`
- Consumes: `ResetConfig` values (passed as primitives).

**Behavior:** `dayFor` returns a stable integer day id that increments at `resetHour` local time in `zone`: take the instant in `zone`, subtract `resetHour` hours, return `toLocalDate().toEpochDay()`. `today()` uses the injected `Clock`. **Tests (write first):** with resetHour=0 UTC, two instants on the same UTC date share a day id and cross-midnight differs by 1; with resetHour=6, 05:59 local is the previous day and 06:00 is the new day; a non-UTC zone shifts the boundary correctly. Use `Clock.fixed`.

**Steps:** (1) failing test; (2) fail; (3) implement; (4) pass; (5) commit `feat(time): server-day boundary clock`.

## Task 5: Streak engine

**Files:** Create `streak/StreakService.java`, `streak/StreakOutcome.java`, `streak/LoginCalendar.java`; Test `streak/StreakServiceTest.java`, `streak/LoginCalendarTest.java`.

**Interfaces:**
- Produces:
  - `record StreakOutcome(int newStreak, boolean streakRewardClaimable, boolean makeUpAvailable, boolean alreadyCountedToday)`.
  - `final class StreakService { StreakService(int forgivenessMisses, boolean makeUpEnabled, int calendarLength); StreakOutcome computeOnJoin(PlayerState state, long today); }`
  - `final class LoginCalendar { LoginCalendar(Map<Integer,List<ItemSpec>> calendar, int length); ItemReward rewardForStreak(int streak); }` — maps streak to calendar day `((streak-1) % length) + 1`; if that exact day has no entry, fall back to the nearest lower defined day (so a sparse calendar still yields a reward).

**Core logic (implement exactly):**
```
computeOnJoin(state, today):
  if state.lastLoginDay == today: return (state.streak, false, false, true)
  int newStreak; boolean makeUp = false;
  if state.lastLoginDay < 0:                      // first ever
      newStreak = 1;
  else:
      long missed = (today - state.lastLoginDay) - 1;   // days with no login between
      if missed <= 0:            newStreak = state.streak + 1;         // consecutive
      elif missed <= forgivenessMisses:
                                 newStreak = state.streak;             // held (forgiven)
                                 makeUp = makeUpEnabled && !state.makeUpUsed;
      else:                      newStreak = Math.max(1, state.streak - 1);  // step down, floor 1
  return (newStreak, true, makeUp, false);
```

**Tests (write first, table-driven):** first login → streak 1, claimable; consecutive day → +1; same day again → alreadyCountedToday, not claimable; one missed day (missed=1, forgiveness=1) → held + makeUp when unused; makeUp not offered when `makeUpUsed` already true or `makeUpEnabled` false; two missed days (missed=2) → streak-1 floored at 1; step-down from streak 1 stays 1. `LoginCalendar`: streak 1/7/14/28 map to the right entries; streak 29 loops to day 1; a streak whose exact day is undefined falls back to the nearest lower defined day.

**Steps:** (1) failing tests; (2) fail; (3) implement; (4) pass; (5) commit `feat(streak): streak computation with forgiveness and make-up`.

## Task 7: Mailbox service

**Files:** Create `mailbox/MailboxService.java`; Test `mailbox/MailboxServiceTest.java`.

**Interfaces:**
- Produces: `final class MailboxService { MailboxService(MailboxDao dao); CompletableFuture<Void> grant(UUID player, ItemReward reward, long day); CompletableFuture<List<PendingReward>> pending(UUID player); CompletableFuture<ClaimResult> claim(UUID player, java.util.function.Function<List<ItemStack>, List<ItemStack>> deposit); }` where `record PendingReward(long id, ItemReward reward)`, `record ClaimResult(int claimedCount, int remainingCount)`.
- Consumes: `MailboxDao` (T4), `RewardCodec`/`ItemReward` (T3).

**Behavior:** `grant` encodes the reward and inserts a mailbox row. `claim` lists unclaimed rewards, and for each calls `deposit` with the reward's ItemStacks; `deposit` returns the leftover stacks that did not fit; a row is `markClaimed` only when its deposit returned empty leftovers (fully delivered), otherwise it stays pending. This keeps inventory-fit logic (a Bukkit concern) injected, so the service is testable with a fake `deposit` function and an in-memory-ish DAO (use the real DAO over a `@TempDir` DB).

**Tests (write first):** grant then pending returns the reward; claim with a deposit that accepts everything marks all claimed and reports remaining 0; claim with a deposit that rejects everything leaves rows pending and reports the remaining count; partial-fit leaves the partially-delivered row pending.

**Steps:** (1) failing test; (2) fail; (3) implement; (4) pass; (5) commit `feat(mailbox): grant/list/claim with partial-delivery`.
